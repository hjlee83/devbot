# Specification: Task 044 — Specification Template Engine

## Provenance

- Task Issue: [#92](https://github.com/hjlee83/devbot/issues/92)

- Generated by the DevBot Architect from the canonical Task Contract and Issue evidence before implementation.

# Overview

## Goal

Add deterministic task-type-aware Specification templates while preserving the single canonical Specification schema established by Tasks 042 and 043.

Templates must improve implementation guidance without creating separate document formats. Every generated output must remain valid under the Task 043 Specification Validator.

## Scope

In scope:

- immutable built-in template registry;
- deterministic Contract-driven selection;
- `feature`, `bugfix`, `refactor`, `docs`, `internal`, and `generic` templates;
- explicit CLI override;
- template inspection commands;
- Generator integration;
- Validator compatibility tests and live evidence.

Out of scope:

- LLM-based classification;
- external/user-authored templates;
- Dispatch or Agent invocation;
- Workflow Engine integration;
- code-to-Spec validation;
- Task 045 release classification;
- broad package migration of existing Specification modules.

## Background

Task 042 created one deterministic generic Specification renderer. Task 043 made its canonical structure enforceable. Task 044 must add template-specific policy as an overlay on that structure rather than replace it.

The target flow is:

`Goal → Planner → Issue → Contract → Template Selection → Specification → Validation → Dispatch`

## Roadmap Context

Task 044 completes the initial Specification Platform sequence before Task 045 changes release classification. It prepares better implementation inputs without yet automating Dispatch.

# Functional Requirements

## Required Behaviour

1. Add a first-class immutable template model and registry.
2. Register exactly six built-in IDs: `feature`, `bugfix`, `refactor`, `docs`, `internal`, and `generic`.
3. Select a template from explicit `## Specification Type` Contract evidence.
4. Normalize explicit values by trimming and lowercasing.
5. Select `generic` only when the field is absent.
6. Fail closed for an unknown explicit value.
7. Support `--template <id>` override for `show` and `generate`.
8. Record selected template ID and selection source in Provenance.
9. Preserve all Task 043 required top-level sections and subsections.
10. Keep canonical section ordering.
11. Make template outputs observably task-specific without inventing missing facts.
12. Keep selection and rendering deterministic and network-free.
13. Add read-only deterministic template list/show CLI commands.
14. Preserve existing no-flag behaviour for historical Contracts.
15. Do not import or invoke Agent, Dispatch, polling, review, or rework components.

## Acceptance Criteria

### CP-044-1 — Registry

- All six built-ins exist exactly once.
- Registry listing is deterministic.
- Unknown lookup fails clearly.

### CP-044-2 — Contract selection

- Every explicit valid type selects the matching template.
- Matching is case-insensitive after trimming.
- Missing type selects `generic`.
- Unknown explicit type fails closed.

### CP-044-3 — CLI override

- Valid override takes precedence over Contract evidence.
- Provenance records override source.
- Invalid override fails.
- Override is read-only with respect to Contract and repository evidence.

### CP-044-4 — Schema compatibility

- Every template includes all canonical sections and required subsections.
- Every template output passes `validate_specification_text`.
- Canonical ordering is unchanged.

### CP-044-5 — Template differentiation

- Feature emphasizes observable behaviour, compatibility, rollout, and migration.
- Bugfix emphasizes reproduction, expected/actual behaviour, fix boundary, and regression protection without invented root cause.
- Refactor emphasizes current/target design, preserved behaviour, and compatibility.
- Docs emphasizes audience, examples, source accuracy, and documentation validation.
- Internal emphasizes operational constraints, observability, safety, and rollback.
- Generic preserves Task 042 historical behaviour.

### CP-044-6 — Generator integration

- `show` and `generate` use selected templates.
- `--dry-run` stays read-only.
- Identical inputs yield byte-identical output.
- Existing Task 042/043 tests retain equivalent coverage.

### CP-044-7 — Inspection CLI

- Template list and show are deterministic and read-only.
- Unknown IDs return non-zero.
- Commands do not acquire the daemon lock.

### CP-044-8 — Scope protection

- No Agent invocation.
- No Dispatch, polling, review, or rework changes.
- No Task 045 implementation.
- No external template execution or network selection.

### CP-044-9 — Live validation

- Representative output for all six templates is generated or shown.
- All six outputs pass Task 043 validation.
- Result document records real commands and outcomes.

### CP-044-10 — Quality gate

- `uv run ruff check .` passes.
- `uv run pytest` passes.

## Out of Scope

# Technical Design

## Architecture

Recommended focused module structure:

```text
src/devbot/
├── specification.py
├── specification_validation.py
└── specification_templates.py
```

`specification_templates.py` should own immutable template policy, registry, and selection. `specification.py` should remain responsible for evidence gathering and canonical rendering orchestration. `specification_validation.py` remains the authoritative structural gate.

Templates are policy overlays. They may supply guidance and evidence mapping but must not own a competing top-level schema.

## Files Expected to Change

Expected:

- `src/devbot/specification_templates.py`
- `src/devbot/specification.py`
- `src/devbot/main.py`
- `tests/test_specification_templates.py`
- `tests/test_specification.py`
- `tests/test_main.py`
- `docs/00-roadmap.md`

Authoritative inputs already committed:

- `tasks/044-specification-template-engine.md`
- `specifications/044-specification-template-engine.md`

## Dependencies

Use the standard library and existing repository dependencies. Do not add Jinja2 or another template engine unless the implementation demonstrates that immutable Python policy objects cannot satisfy the Contract; such a dependency would require explicit architectural review.

## Constraints

- Task 043 schema is authoritative.
- Selection uses explicit Contract evidence only.
- Missing type means `generic`; unknown explicit type fails.
- Output and registry ordering must be deterministic.
- Rendering and inspection are read-only and network-free.
- No speculative root cause, rollout, compatibility, or requirement content may be invented.
- Avoid broad restructuring of Tasks 042 and 043 modules.

## Migration Notes

This is additive. Historical Contracts without `Specification Type` continue through `generic`. No persistent migration or historical rewrite is required.

Rollback is a revert of Task 044 commits.
