# Task 005 Improvement Suggestions

## 애매했던 요구사항

- `tasks/005-main-loop.md`에 서로 다른 두 버전(상세 한국어 v1.0.0 12개
  체크포인트 + 이전 영어 초안 6개 체크포인트)이 함께 남아있었다. 사용자
  확인 후 한국어 v1.0.0을 채택하고 영어 초안은 삭제했다. 이후 Task
  문서를 열 때는 파일 전체를 끝까지 읽어 이런 중복/충돌이 없는지 먼저
  확인하는 습관이 필요해 보인다.
- "GlobalQueue"/"WorkspaceManager"를 의존성 주입 대상으로 명시했는데,
  실제로는 Task 001/003/004에서 이미 순수 함수(`select_global_ready_task`,
  `ensure_git_workspace_ready`)로 구현돼 있었다. 이걸 클래스로 감싸는
  대신, 함수 자체를 기본값으로 갖는 생성자 파라미터로 주입 가능하게
  만드는 쪽을 택했다 — "대체 가능해야 한다"는 요구사항은 만족하면서
  이미 테스트가 통과한 Task 001/003/004의 API를 건드리지 않기 위함이다.
  만약 실제로 클래스 기반 인터페이스가 필요했다면 이 선택이 틀렸을 수
  있다.
- "결과 모델 예시 상태"에 `TASK_SELECTED`가 있었지만, 실제 흐름에서는
  선택 이후 항상 워크스페이스 검증이나 에이전트 실행으로 곧장 이어지기
  때문에 "선택은 됐지만 그 이상 진행하지 않은" 상태가 별도로 존재하지
  않는다. `TASK_SELECTED`를 별도 터미널 상태로 두지 않고, 최종 상태가
  무엇이든 `PollingResult.task`에 선택된 Issue 정보를 항상 채우는
  방식으로 "선택이 일어났다"는 사실을 표현했다.
- `GITHUB_TOKEN`을 어디까지 검증해야 하는지(형식 검사 등) 명시가 없어,
  Task 001의 `WORKSPACE_ROOT`와 동일하게 "비어있지 않은 문자열"만
  확인했다. 실제 토큰 유효성은 GitHub API 호출 시점에 자연히 검증된다.

## 추가하면 좋을 품질 게이트

- CLI의 기본 동작이 Task 005에서 완전히 바뀌었다(플래그 없는 실행이
  "1회 실행 후 종료"에서 "연속 폴링"으로). 이렇게 이전 Task의 CLI 계약을
  깨는 변경이 있을 때, Task 문서에 "이 Task는 Task 00N의 CLI 동작을
  대체한다"처럼 명시적으로 표시해주면 이전 Task의 필수 테스트를 얼마나
  또 어떻게 바꿔도 되는지 판단하기 쉬워질 것 같다.
- CI에서 `uv run devbot`(인자 없음)을 그대로 실행하면 연속 모드로 들어가
  영원히 끝나지 않는다. 검증 스크립트/CI 워크플로가 항상 `--once`를
  쓰도록 강제하는 장치(예: 스크립트에 타임아웃을 걸어두는 것)가 있으면
  이런 실수를 더 빨리 잡을 수 있을 것 같다. 이번엔 로컬에서 먼저
  발견해서 CI에 반영했지만, 발견이 늦었으면 CI가 그냥 무한정 걸려있었을
  것이다.

## 누락된 경계 조건

- `run_forever`가 `run_once()` 자체에서 발생하는 예상치 못한 예외(예:
  `has_active_task`나 `select_task`가 직접 예외를 던지는 극단적인 경우)를
  잡지 않는다 — `run_once()`가 항상 예외를 삼키고 `PollingResult`를
  반환한다는 계약에 의존한다. `run_once()` 자체의 방어 로직이 깨지면
  `run_forever`도 함께 죽는다. 이건 의도한 설계(각 계층이 자기 책임만
  진다)지만, 명시적으로 테스트하지는 않았다.
- 매우 짧은 `poll_interval_seconds`(예: 0 또는 음수)에 대한 경계 테스트를
  추가하지 않았다. Task 005의 "최소 polling interval" 경계 조건 요구를
  `test_continuous_loop_uses_configured_poll_interval`이 특정 값(42)을
  정확히 전달하는지로 대체 검증했는데, "설정 가능한 최솟값이 얼마인지"
  자체는 Task 문서에 명시돼 있지 않아 별도 하한 검증은 넣지 않았다.
